# Introduction

The **Six Solution Template** provides a set of predefined configuration files that handle the most important 
aspects of .NET development.

This page explains each configuration file, what it configures, and how to customize it for your specific needs.

<Aside type="tip">
    Most configuration files work out of the box. Only modify them when you have specific requirements that differ from the template defaults.
</Aside>


# Directory.Build.props

The template implements a hierarchical MSBuild configuration system using `Directory.Build.props` files. 
This creates a layered approach where settings cascade from general to specific, ensuring consistency while allowing customization.

## Root Directory.Build.props

The master configuration file **in the solution root** establishes baseline settings for all projects:

```xml
<!-- Root Directory.Build.props - Master configuration -->
<Project>
<PropertyGroup>
    <LangVersion>13</LangVersion>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
</PropertyGroup>

    <!-- StyleCop configuration -->
    <PropertyGroup>
        <CodeAnalysisRuleSet>$(MSBuildThisFileDirectory)rules.ruleset</CodeAnalysisRuleSet>
        <StyleCopTreatErrorsAsWarnings>false</StyleCopTreatErrorsAsWarnings>
    </PropertyGroup>

    <!-- CI/CD optimizations -->
    <PropertyGroup Condition="'$(CI)' == 'true'">
        <ContinuousIntegrationBuild>true</ContinuousIntegrationBuild>
        <Deterministic>true</Deterministic>
    </PropertyGroup>
</Project>
```

**What it configures**:
- **Language version** (C# 13)
- **Code quality settings** (nullable types, warnings as errors)
- **StyleCop integration** for code style enforcement
- **CI/CD optimizations** for deterministic builds

## Project-Specific Directory.Build.props

Individual directories contain specialized configurations:

### libs/Directory.Build.props

```xml
<!-- libs/Directory.Build.props - Library-specific settings -->
<Project>
    <Import Project="$(MSBuildThisFileDirectory)../Directory.Build.props" />

    <PropertyGroup>
        <IsPackable>true</IsPackable>
        <GeneratePackageOnBuild>false</GeneratePackageOnBuild>
        <IncludeSymbols>true</IncludeSymbols>
        <SymbolPackageFormat>snupkg</SymbolPackageFormat>
    </PropertyGroup>

    <!-- Source Link for debugging -->
    <ItemGroup>
        <PackageReference Include="Microsoft.SourceLink.GitHub" Version="8.0.0" PrivateAssets="All" />
    </ItemGroup>
</Project>
```

**What it configures**:
- **NuGet packaging** settings for libraries
- **Symbol packages** for debugging support
- **Source Link** integration for source code debugging

### tests/Directory.Build.props

```xml
<!-- tests/Directory.Build.props - Test-specific settings -->
<Project>
    <Import Project="$(MSBuildThisFileDirectory)../Directory.Build.props" />

    <PropertyGroup>
        <IsPackable>false</IsPackable>
        <IsTestProject>true</IsTestProject>
    </PropertyGroup>

    <!-- Code coverage configuration -->
    <PropertyGroup>
        <CollectCoverage>true</CollectCoverage>
        <CoverletOutputFormat>cobertura;html</CoverletOutputFormat>
        <Threshold>80</Threshold>
    </PropertyGroup>
</Project>
```

**What it configures**:
- **Test project identification** for build systems
- **Code coverage collection** settings
- **Coverage thresholds** and output formats

## How the Hierarchy Works

The configuration hierarchy follows this pattern:

1. **Root Directory.Build.props** - Base settings for all projects
2. **Directory-specific Directory.Build.props** - Specialized settings that import and extend the root
3. **Individual project files** - Final customizations for specific projects

```xml
<!-- Example: A library project inherits from both levels -->
<Project Sdk="Microsoft.NET.Sdk">
    <!-- This automatically imports ../Directory.Build.props -->
    <!-- Which in turn imports ../../Directory.Build.props -->

    <PropertyGroup>
        <TargetFramework>net9.0</TargetFramework>
        <!-- Project-specific overrides here -->
    </PropertyGroup>
</Project>
```

# global.json

The `global.json` file ensures all developers and CI systems use the same .NET SDK version, preventing version drift and build inconsistencies.

<Aside type="note">
    Currently we are using **.NET 10 preview** as the default SDK version since we are **using File-Based apps for 
    scripting.**
    
    As soon .NET 10 is GA, we will update the template to use it without `allowPrerelease` flag.
</Aside>

## Configuration Structure

```json
{
  "sdk": {
    "version": "10.0.100-preview.7",
    "rollForward": "latestMinor",
    "allowPrerelease": true
  }
}
```

## What It Configures

**SDK Version Pinning**:
- **version**: Specific SDK version to use
- **rollForward**: How to handle version mismatches
- **allowPrerelease**: Whether to allow preview/beta versions

## RollForward Options

```json
{
  "sdk": {
    "version": "8.0.100",
    "rollForward": "latestPatch"     // Use latest patch version
    // "rollForward": "latestMinor"   // Use latest minor version
    // "rollForward": "latestMajor"   // Use latest major version
    // "rollForward": "disable"       // Exact version match only
  }
}
```

## Why This Matters

- **Reproducible Builds**: Same SDK version across all environments
- **Feature Consistency**: All developers have access to the same language features
- **CI/CD Reliability**: Builds work identically in development and production
- **Version Drift Prevention**: Avoids "works on my machine" issues

## Customizing global.json

To change the SDK version for your project:

```json
{
  "sdk": {
    "version": "9.0.100",           // Change to your preferred version
    "rollForward": "latestPatch",   // More conservative rollForward
    "allowPrerelease": false        // Disable prerelease versions
  }
}
```

<Aside type="note">
    After changing global.json, run `dotnet --info` to verify the correct SDK is being used.
</Aside>

# nuget.config

The `nuget.config` file provides a complete package management strategy with environment-specific feeds and 
secure credential management using environment variables.

<Aside type="tip">
    Learn more about how we handle NuGet feeds and secrets in the [NuGet Feeds](../../nuget-feeds/nuget-feeds)
    and [NuGet Secrets](../../nuget-feeds/nuget-secrets) docs.    
</Aside>

## Configuration Structure

```xml
<configuration>
    <packageSources>
        <clear />
        <add key="Local" value="%NUGET_FEED_LOCAL_URL%" />
        <add key="Development" value="%NUGET_FEED_DEV_URL%" />
        <add key="Staging" value="%NUGET_FEED_STAGING_URL%" />
        <add key="Production" value="%NUGET_FEED_PRODUCTION_URL%" />
    </packageSources>

    <packageSourceCredentials>
        <Development>
            <add key="Username" value="%NUGET_FEED_DEV_USERNAME%" />
            <add key="ClearTextPassword" value="%NUGET_FEED_DEV_PAT%" />
        </Development>
        <Staging>
            <add key="Username" value="%NUGET_FEED_STAGING_USERNAME%" />
            <add key="ClearTextPassword" value="%NUGET_FEED_STAGING_PAT%" />
        </Staging>
        <Production>
            <add key="Username" value="%NUGET_FEED_PRODUCTION_USERNAME%" />
            <add key="ClearTextPassword" value="%NUGET_FEED_PRODUCTION_PAT%" />
        </Production>
    </packageSourceCredentials>
</configuration>
```

## What It Configures

**Package Sources**:
- **Local**: Development packages stored locally
- **Development**: Internal development feed
- **Staging**: Pre-production package validation
- **Production**: Public or private production feed

**Authentication**:
- **Environment Variables**: Secure credential storage
- **Multiple Environments**: Different credentials per environment
- **Token-Based Auth**: Personal Access Tokens (PAT) for security


## Why This Matters

- **Environment Separation**: Clear boundaries between development stages
- **Security**: No hardcoded credentials in source control
- **Flexibility**: Easy to add/remove feeds without code changes
- **CI/CD Integration**: Different feeds for different pipeline stages

## Customizing nuget.config

To add a new feed or modify existing ones:

```xml
<configuration>
    <packageSources>
        <clear />
        <add key="Local" value="%NUGET_FEED_LOCAL_URL%" />
        <add key="Development" value="%NUGET_FEED_DEV_URL%" />
        <!-- Add your custom feed -->
        <add key="CustomFeed" value="https://your-custom-feed.com/v3/index.json" />
    </packageSources>

    <packageSourceCredentials>
        <!-- Add credentials for your custom feed -->
        <CustomFeed>
            <add key="Username" value="%CUSTOM_FEED_USERNAME%" />
            <add key="ClearTextPassword" value="%CUSTOM_FEED_PAT%" />
        </CustomFeed>
    </packageSourceCredentials>
</configuration>
```

<Aside type="danger">
    **Warning**: Never commit actual credentials to source control. Always use environment variables.
</Aside>

# StyleCop Integration

The StyleCop configuration is located in the `stylecop.json` file in the solution root. This file enforces consistent code style and documentation standards across all C# projects.

## Configured Rules

The template configures only few of the following StyleCop rules in `stylecop.json`:

```json
{
  "settings": {
    "orderingRules": {
      "blankLinesBetweenUsingGroups": "omit"
    },
    "documentationRules": {
      "companyName": "Six",
      "copyrightText": "Copyright (c) {companyName}. All rights reserved.\nLicensed under the {licenseName} license. See {licenseFile} file in the project root for full license information.",
      "variables": {
        "licenseName": "MIT",
        "licenseFile": "License.txt"
      },
      "documentInternalElements": false,
      "documentationCulture": "en-GB"
    }
  }
}
```

### What Each Rule Does

- **blankLinesBetweenUsingGroups**: Controls spacing between using directive groups
- **companyName**: Sets the company name for copyright headers
- **copyrightText**: Defines the copyright text template with variables
- **variables**: Defines reusable variables for copyright text (license name and file)
- **documentInternalElements**: Whether to require documentation for internal elements
- **documentationCulture**: Culture for documentation text (en-GB)

## Disabling Specific Rules

To disable specific StyleCop rules for your project:

```xml
<!-- In Directory.Build.props -->
<PropertyGroup>
    <NoWarn>$(NoWarn);SA1600;SA1633</NoWarn>  <!-- Disable specific StyleCop warnings -->
</PropertyGroup>
```

# .editorconfig

The `.editorconfig` file in the solution root establishes consistent coding styles and formatting rules that work across different editors and IDEs.

## Configured Rules

The template configures comprehensive formatting rules for C# files:

### .NET Coding Conventions

```ini
# Organize usings
dotnet_separate_import_directive_groups = false
dotnet_sort_system_directives_first = true

# this. and Me. preferences
dotnet_style_qualification_for_event = false
dotnet_style_qualification_for_field = false
dotnet_style_qualification_for_method = false
dotnet_style_qualification_for_property = false

# Language keywords vs BCL types preferences
dotnet_style_predefined_type_for_locals_parameters_members = true
dotnet_style_predefined_type_for_member_access = true

# Modifier preferences
dotnet_style_require_accessibility_modifiers = never:suggestion

# Expression-level preferences
dotnet_style_coalesce_expression = true
dotnet_style_collection_initializer = true
dotnet_style_null_propagation = true
dotnet_style_object_initializer = true
dotnet_style_prefer_auto_properties = true
dotnet_style_readonly_field = true
```

### C# Coding Conventions

```ini
# var preferences
csharp_style_var_elsewhere = false
csharp_style_var_for_built_in_types = false:silent
csharp_style_var_when_type_is_apparent = false:silent

# Expression-bodied members
csharp_style_expression_bodied_accessors = true:silent
csharp_style_expression_bodied_properties = true:silent
csharp_style_expression_bodied_lambdas = true:silent

# Pattern matching preferences
csharp_style_prefer_switch_expression = true
csharp_style_prefer_pattern_matching = true

# Modifier preferences
csharp_prefer_static_local_function = true
csharp_style_prefer_readonly_struct = true
```

### C# Formatting Rules

```ini
# Indentation preferences
csharp_indent_block_contents = true
csharp_indent_braces = false
csharp_indent_case_contents = true

# Space preferences
csharp_space_after_cast = false
csharp_space_after_keywords_in_control_flow_statements = false
csharp_space_after_comma = true
csharp_space_after_dot = false

# New line preferences
csharp_new_line_before_open_brace = all
csharp_new_line_before_else = true
csharp_new_line_before_catch = true
```

### Naming Conventions

```ini
# Interface naming
dotnet_naming_rule.interface_should_be_begins_with_i.severity = suggestion
dotnet_naming_rule.interface_should_be_begins_with_i.symbols = interface
dotnet_naming_rule.interface_should_be_begins_with_i.style = begins_with_i

# Private fields naming
dotnet_naming_rule.private_fields_should_be_camel_case_with_underscore.symbols = private_fields
dotnet_naming_rule.private_fields_should_be_camel_case_with_underscore.style = camel_case_underscore_prefix
dotnet_naming_rule.private_fields_should_be_camel_case_with_underscore.severity = suggestion
```

### File Format Standards

```ini
# Root configuration
root = true

[*.{cs,vb}]
dotnet_style_operator_placement_when_wrapping = beginning_of_line
tab_width = 1
indent_size = 2
end_of_line = crlf
insert_final_newline = false
indent_style = space
```

## Key Settings Summary

- **Indentation**: 2 spaces for C# files
- **Line endings**: CRLF (Windows-style)
- **Naming**: Interfaces prefixed with 'I', private fields with '_'
- **Braces**: All on new lines
- **var usage**: Conservative (prefer explicit types)
- **Expression-bodied members**: Preferred for accessors and properties
- **Pattern matching**: Enabled for modern C# features


### Customizing .editorconfig

To modify formatting rules for your project:

```ini
# Example: Change indentation to 4 spaces
[*.cs]
indent_size = 4

# Example: Enable var everywhere
[*.cs]
csharp_style_var_elsewhere = true
csharp_style_var_for_built_in_types = true
csharp_style_var_when_type_is_apparent = true
```

# AGENTS.md

The `AGENTS.md` file serves as the primary interface between AI coding agents and the project, providing comprehensive context and guidance.

The `AGENTS.md` file enables AI agents to:

1. **Understand Context**: Quickly grasp project architecture and requirements
2. **Follow Standards**: Apply consistent coding and architectural patterns
3. **Execute Tasks**: Run appropriate commands for different development activities
4. **Maintain Quality**: Adhere to project's quality and testing standards
5. **Communicate Effectively**: Use project-specific terminology and conventions

<Aside type="tip">
    Keep AGENTS.md updated whenever you change project structure, add new tools, or modify development processes.
</Aside>


## Structure Overview

```markdown
# AGENTS.md

## Project Overview
[High-level project description, tech stack, architecture]

## Development Environment
[Prerequisites, setup instructions, tool requirements]

## Build and Test Instructions
[Commands for building, testing, and running the project]

## Code Standards and Conventions
[Coding guidelines, patterns, and best practices]

## Project Structure
[Directory layout, file organization, key components]

## Common Tasks
[Step-by-step guides for frequent development tasks]

## Troubleshooting
[Common issues and their solutions]
```

## What It Contains

**Project Context**:
- **Technology Stack**: Languages, frameworks, and tools used
- **Architecture Overview**: High-level system design and components
- **Development Workflow**: How the team works and processes

**Technical Guidance**:
- **Setup Instructions**: How to get the project running locally
- **Build Commands**: Specific commands for different development tasks
- **Testing Procedures**: How to run tests and what they cover
- **Deployment Process**: How to deploy changes to different environments

**Coding Standards**:
- **Code Style**: Formatting, naming conventions, and patterns
- **Best Practices**: Recommended approaches and anti-patterns
- **Quality Gates**: Code review requirements and automated checks


## Customizing AGENTS.md

To update AGENTS.md for your project's specific needs:

```markdown
## Project Overview

## Technology Stack
- **Frontend**: React 18, TypeScript, Tailwind CSS
- **Backend**: .NET 8, ASP.NET Core, Entity Framework
- **Database**: PostgreSQL 15
- **Infrastructure**: Docker, Kubernetes, Azure

## Key Features
- User authentication and authorization
- Real-time notifications
- File upload and processing
- RESTful API design
```
